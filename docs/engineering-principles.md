# 工程原则

> **来源**:迁移自 `pre-speckit-removal:.specify/memory/constitution.md`
> **迁移日期**:2026-11-03
> **原版本**:1.0.0;原批准日期:2026-07-28;原最后修订:2026-07-28

本文档记录 Moss Guide 书签导航的工程原则、理由与执行含义。它从原工作流文档中提炼而来,不再依赖任何已移除的流程或命令。日常操作细则(逐行编码、测试与验收的工作约定)见仓库根 `CLAUDE.md`;本文档只保留原则层面的约束。

## 核心原则

### 先思考再编码

**要求**

- 实现前必须显式陈述假设;不确定时必须询问用户,不得默默选择。
- 存在多种合理解读时,必须一并列出,交由用户裁决,不得擅自挑其一。
- 发现更简方案时,必须提出,必要时反驳用户方案。
- 感到困惑时,必须停下,命名困惑点并提问,不得带着糊涂实现。

**理由**

LLM 常见失败模式是"默默假设后大规模返工"。把澄清前置到实现之前,代价远低于实现之后的纠正。

### 简洁优先

**要求**

- 仅交付被要求的功能,不得引入未被请求的特性、抽象、灵活性或配置项。
- 一次性使用的代码不得被抽象。
- 不可能发生的场景不得编写错误处理。
- 若 200 行能压缩为 50 行,必须重写。
- 设计与计划必须通过"资深工程师是否会认为过度复杂"的自检。

**理由**

投机性代码增加阅读、测试与维护成本,且常常从未被使用。YAGNI。

### 外科手术式改动

**要求**

- 每一处改动必须能直接追溯到用户请求。
- 不得顺手"改进"相邻代码、注释或格式;不得重构未坏之物。
- 必须匹配既有风格,即便个人偏好不同。
- 发现无关死代码时,应提示用户,但不得擅自删除。
- 因自身改动而产生的孤儿(未用 import / 变量 / 函数)必须清理;既有死代码不得删除,除非被明确要求。

**理由**

无关改动污染 diff、抬升评审成本、引入回归风险。每一行变更都应能追溯到需求。

### 目标驱动执行

**要求**

- 每个任务必须被转化为可验证目标(成功标准);"让它能用"之类的弱标准不得作为收尾依据。
- 修复缺陷必须先写复现测试再修复。
- 新增校验必须先写失败测试再实现。
- 重构必须确保前后测试均通过。
- 多步任务必须给出带校验点的简短计划,形如:`步骤 → 验证: [检查]`。

**理由**

强成功标准让代理能独立循环到完成;弱标准迫使反复澄清,且常以"看起来好了"掩盖未覆盖的边界。

## 语言与文档约束

- 与用户的对话回复及所有生成的文档必须使用中文。
- 代码标识符(变量、函数、类型、文件名、组件名)必须使用英文;字符串字面量与注释优先中文,若与既有代码风格冲突则跟随既有风格。
- 文档与代码混排时,必须保持标识符为原文英文,说明性文字为中文;不得将英文标识符机械翻译为中文。
- Git 提交信息必须使用英文 Conventional Commits 风格(遵循仓库既有约定,如 `feat:` / `fix:` / `chore:`)。
- 运行期混合语言的具体操作规则见仓库根 `CLAUDE.md`;本文档仅立原则,不重复其操作细节。

## 质量门与验收

- 收尾前必须依次通过 `pnpm lint`(零警告)、`pnpm typecheck`、`pnpm test`。
- 类型变更或公开 API 变更必须同步受影响的单元 / 集成测试。
- 验收必须对照 [质量基线](./quality-baseline.md) 中的验收判定逐条勾验;不得以"能运行"替代对照验收。原需求文档仅作历史归档,见 `docs/archive/spec-kit/`。
- 涉及用户路径的 UI 变更应补充 Playwright E2E 用例(位于 `tests/e2e/`)。
- 发现既有代码违反本文档原则时,必须先向用户陈述问题、原因、修改方案,获确认后再改。

## 治理

- 本文档所述原则优先于本仓库的其他实践;设计、计划与任务拆解必须与之一致,出现冲突以本文档为准。若原则本身需要变更,必须通过单独、显式的原则文档更新完成,不得在评审或实现过程中悄悄稀释或重新解释。
- 修订必须记录变更内容与迁移计划,并按语义化版本递增:
  - `MAJOR`:原则删除或重定义(向后不兼容);
  - `MINOR`:新增原则或实质性扩展;
  - `PATCH`:措辞、笔误、非语义澄清。
- 所有计划评审必须逐条核对本文档原则;任何复杂度都必须有正当理由支撑。
- 运行期开发指引见仓库根 `CLAUDE.md`,其承载逐行编码、测试与验收的工作约定;本文档不重复其内容。
