# Feature Specification: 前端显示层 UI/UX 系统性优化

**Feature Branch**: `001-ui-ux-overhaul`

**Created**: 2026-07-28

**Status**: Draft

**Input**: User description: "对当前项目前端显示层进行 UI/UX 系统性优化,覆盖视觉、交互、适配、性能四维度。强制约束:沿用当前设计。具体优化细节由后续 clarify 确认。"

## Clarifications

### Session 2026-07-28

- Q: 色彩体系调整幅度? → A: 保留橙色 primary 与 HSL 变量体系,校准明度/对比度达 WCAG AA,并补全 success/warning/info 语义色阶。
- Q: 字体排版调整幅度? → A: 沿用系统字体栈,补齐 type scale(显示/标题/正文/辅助四档)、行高、字重梯度与中文优化字距,文档化为 token。
- Q: 圆角与阴影风格调整幅度? → A: 统一圆角阶梯(sm/md/lg 映射现有 --radius)与四档阴影 elevation(sm/md/lg/popover),文档化为 token。
- Q: 深色模式支持力度? → A: 沿用三态切换 + matchMedia 监听,补全无障碍可达性与 FOUC 防护。
- Q: 视觉层状态反馈如何落地? → A: 加载/空/错误三类状态统一为占位组件 + 引导动作,配色走新增的语义色阶。

### Session 2026-07-28(交互层)

- Q: 书签卡片点击打开策略? → A: 整卡单击即在新标签打开,强化悬停/聚焦的"可点击"反馈(升降/阴影/光晕)。
- Q: 搜索框聚焦与输入体验升级方向? → A: Ctrl+K 弹出全屏命令面板,含列表 + 键盘上下选择 + Enter 跳转(Spotlight/Raycast 风格)。
- Q: 分类导航呈现效果? → A: PC 侧栏增加可折叠(收起/展开)与计数 badge 高亮,不改两套布局分支结构。
- Q: 破坏性操作确认方式? → A: 删除书签/分类仍弹 AlertDialog 二次确认,默认焦点落在"取消"上,Enter 不触发删除。
- Q: 操作反馈提示方式? → A: 沿用 toast(成功/失败),统一出现位置/时序/语义色,与新增语义色阶呼应。

### Session 2026-07-28(适配层)

- Q: 响应式断点策略? → A: 沿用 Tailwind 默认断点梯度(sm 640 / md 768 / lg 1024 / xl 1280 / 2xl 1536),补全中间档(md 768 平板)。
- Q: 移动端触摸热区? → A: 强制所有可交互元素最小热区 44×44px(WCAG 2.5.5),通过 padding/min-h-* 补齐偏小按钮。
- Q: 横竖屏适配? → A: 适配但靠响应式断点宽度驱动,横屏自动进桌面分支,不单独做横屏布局。
- Q: 小屏设备导航栏折叠逻辑? → A: 移动端底部固定 Tab(全部/分类)+ 侧滑抽屉承载完整分类列表。

### Session 2026-07-28(性能层)

- Q: 首屏加载时间目标? → A: 首屏可交互(TTI)< 2 秒(中端移动 + 3G 慢速模拟),LCP 维持 < 1.5s。
- Q: 图片/资源懒加载策略? → A: favicon 走原生 `loading="lazy"` + `decoding="async"` + `onError` 降级;书签列表走虚拟滚动(大数据量)。
- Q: 渲染策略(SSR/预渲染)? → A: 沿用纯 CSR(Vite SPA),不做 SSR/预渲染,靠代码分割 + 懒加载 + 虚拟滚动达标。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 视觉打磨 (Priority: P1)

作为日常使用书签导航的用户,我希望界面在视觉上更精致、更一致(间距、对齐、层次、配色对比、状态反馈),以便长时间使用不疲劳、关键信息一眼可辨。

**Why this priority**: 视觉是用户对"好不好用"的第一感知,且打磨风险低、可独立交付,是其余三维度的基础。

**Independent Test**: 在亮色与暗色主题下,逐屏检查间距/对齐/对比度/状态(悬停、聚焦、选中、加载、空、错误)是否统一且符合无障碍对比标准;可由设计走查清单逐条勾验,无需依赖其他维度。

**Acceptance Scenarios**:

1. **Given** 任一卡片处于悬停态, **When** 鼠标移入移出, **Then** 悬停反馈一致且与同层级其他可交互元素风格统一。
2. **Given** 当前为暗色主题, **When** 走查所有文本与其背景, **Then** 正文文本对背景对比度不低于 WCAG AA(正常文本 4.5:1,大文本 3:1)。
3. **Given** 列表正在加载, **When** 数据未到, **Then** 展示统一的加载占位,而非空白或闪烁。
4. **Given** 列表为空或搜索无结果, **When** 进入该状态, **Then** 展示明确的空状态(含引导动作),而非空白。

---

### User Story 2 - 交互体验提升 (Priority: P2)

作为高频使用书签导航的用户,我希望键盘操作、焦点流、反馈时序、错误提示更顺手,以便快速完成任务且少出错。

**Why this priority**: 交互紧贴视觉之后,直接影响效率与可达性;可与视觉解耦独立交付。

**Independent Test**: 仅用键盘完成"添加书签 → 编辑 → 删除 → 搜索 → 切换分类 → 切换主题"全流程;检查焦点可见、顺序合理、反馈及时、错误可恢复,不依赖视觉打磨项。

**Acceptance Scenarios**:

1. **Given** 焦点在任意可交互元素, **When** 用 Tab/Shift+Tab 遍历, **Then** 焦点可见、顺序符合阅读流、不跳到隐藏元素。
2. **Given** 用户触发删除等破坏性操作, **When** 弹出确认, **Then** 可用键盘完成确认/取消,且默认焦点落在非破坏选项上。
3. **Given** 操作失败(如保存书签失败), **When** 错误发生, **Then** 以非阻塞提示告知原因且不丢失已填输入。
4. **Given** 用户执行快捷键(如新建书签), **When** 按下组合键, **Then** 行为一致且不与浏览器/系统默认冲突。

---

### User Story 3 - 响应式与适配增强 (Priority: P3)

作为在不同设备(桌面/平板/手机、不同视口与偏好)上使用书签导航的用户,我希望布局与组件在各视口下都合理、不溢出、不错位,并尊重系统偏好(主题、动效降级),以便在任何设备上都可用。

**Why this priority**: 适配在视觉与交互稳定后更易收敛;当前已有 PC/移动两套布局分支,需补全中间断点与边界。

**Independent Test**: 在一组标准视口宽度(如 360 / 480 / 768 / 1024 / 1440 px)与系统偏好(浅/深、减少动效)下逐档截图走查,无需依赖性能或视觉细节项。

**Acceptance Scenarios**:

1. **Given** 视口宽度在任一标准断点附近, **When** 横向拖动窗口宽度, **Then** 布局平滑切换、无横向滚动条、无内容溢出。
2. **Given** 用户系统开启"减少动效", **When** 触发动画/过渡, **Then** 动画被降级或省略,不影响功能。
3. **Given** 移动端使用底部导航/标签栏, **When** 单手操作, **Then** 关键操作在拇指可达区内。
4. **Given** 文本或长标题超出容器, **When** 渲染, **Then** 以省略或换行优雅处理,不破坏布局。

---

### User Story 4 - 前端性能优化 (Priority: P4)

作为加载与响应速度敏感的用户,我希望首屏更快、交互更跟手、无布局抖动,以便大量书签下仍流畅。

**Why this priority**: 性能在前三维度稳定后更易归因与度量;作为兜底维度独立验收。

**Independent Test**: 在含大量书签(如 500+ 条)的数据集下,用通用 Web 指标基线测量首屏与交互响应,不依赖其他维度。

**Acceptance Scenarios**:

1. **Given** 冷启动加载书签数据, **When** 首屏渲染, **Then** 首屏最大内容绘制(LCP)低于通用基线 1.5 秒。
2. **Given** 用户执行搜索/筛选/拖拽, **When** 交互发生, **Then** 每次交互到下一帧响应(INP)低于 200 毫秒。
3. **Given** 列表加载或筛选, **When** 内容插入, **Then** 累计布局偏移(CLS)低于 0.1。
4. **Given** 大数据量列表滚动, **When** 快速滚动, **Then** 无明显掉帧(主观流畅,基线 60fps)。

---

### Edge Cases

- 数据为空(零书签、零分类)时各维度表现如何?
- 单条书签字段极端(超长标题/无 favicon/无效 URL)时视觉与布局如何?
- 暗色与亮色主题切换瞬间是否出现闪烁(FOUC)?
- 网络资源(favicon)加载失败时的降级展示?
- 隐私/无痕模式下的提示是否仍可达且不阻塞?
- 横竖屏切换瞬间布局是否平滑过渡(靠宽度驱动断点,不单独渲染)?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在视觉维度提供统一的间距、对齐、层次与状态反馈规范,并在所有界面元素上一致落地。
  - 色彩:保留现有橙色 primary 与 HSL 变量体系,校准明度/对比度达 WCAG AA,并补全 success/warning/info 语义色阶,文档化为 token。
  - 字体:沿用系统字体栈,补齐 type scale(显示/标题/正文/辅助四档)、行高、字重梯度与中文优化字距,文档化为 token。
  - 圆角/阴影:统一圆角阶梯(sm/md/lg 映射现有 `--radius`)与四档阴影 elevation(sm/md/lg/popover),文档化为 token。
- **FR-002**: 系统 MUST 保证所有正文文本在亮色与暗色主题下对背景对比度符合 WCAG AA。
- **FR-003**: 系统 MUST 为加载、空、错误等状态提供统一的占位/提示呈现,配色走语义色阶,含引导动作。
- **FR-004**: 系统 MUST 支持仅用键盘完成核心流程(增删改查、搜索、分类切换、主题切换)。
- **FR-005**: 系统 MUST 保证焦点可见、顺序合理、不跳至隐藏元素。
- **FR-006**: 系统 MUST 以非阻塞方式呈现操作反馈与错误提示,且错误下不丢失用户输入。
  - 反馈:沿用 toast(成功/失败),统一出现位置、时序与语义色阶。
  - 破坏性确认:删除书签/分类 MUST 弹 AlertDialog 二次确认,默认焦点落在"取消"上,Enter 不触发删除。
- **FR-007**: 系统 MUST 在标准视口断点集合下无横向溢出、无错位,布局平滑切换。
  - 断点:沿用 Tailwind 默认梯度(sm 640 / md 768 / lg 1024 / xl 1280 / 2xl 1536),补全中间档(md 768 平板)。
- **FR-008**: 系统 MUST 尊重"减少动效"等系统偏好,降级非必要动画。
- **FR-009**: 系统 MUST 在大数据量(500+ 书签)下满足首屏 LCP < 1.5s、首屏可交互(TTI)< 2s(中端移动 + 3G 慢速模拟)、交互 INP < 200ms、CLS < 0.1 的基线。
- **FR-010**: 系统 MUST 对极端字段值(超长标题、favicon 缺失/失败、无效 URL)做优雅降级,不破坏布局。
- **FR-011**: 系统 MUST 防止主题切换时的 FOUC(无样式内容闪烁),保证主题在首屏渲染前确定。
- **FR-018**: 系统 MUST 对 favicon 走原生 `loading="lazy"` + `decoding="async"` + `onError` 降级(沿用现有 fallbackIcon),并在大数据量书签列表启用虚拟滚动。
- **FR-019**: 系统 MUST 沿用纯 CSR(Vite SPA),不做 SSR/静态预渲染;性能基线靠代码分割 + 懒加载 + 虚拟滚动达成。
- **FR-012**: 书签卡片 MUST 整卡单击即在新标签打开,并强化悬停/聚焦的"可点击"反馈(升降/阴影/光晕)。
- **FR-013**: 搜索 MUST 支持 Ctrl+K 弹出全屏命令面板,含结果列表 + 键盘上下选择 + Enter 跳转 + Esc 关闭。
- **FR-014**: 分类导航 MUST 支持 PC 侧栏可折叠(收起/展开)与计数 badge 高亮,不改两套布局分支结构。
- **FR-015**: 系统 MUST 保证 toast 反馈在亮/暗主题下出现位置、时序、语义色一致。
- **FR-016**: 系统 MUST 保证移动端所有可交互元素最小触摸热区 44×44px(WCAG 2.5.5),通过 padding/min-h-* 补齐偏小按钮。
- **FR-017**: 移动端导航 MUST 采用底部固定 Tab(全部/分类)+ 侧滑抽屉承载完整分类列表,替代当前顶部横向滚动标签栏。

### Key Entities

本次为显示层优化,不新增数据实体。涉及既有实体的展示属性:

- **书签(Bookmark)**: 标题、URL、favicon、分类、最近访问等展示字段在视觉/适配/性能维度下的呈现约束。
- **分类(Category)**: 名称、计数、选中/悬停态在导航与拖放交互中的反馈。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 视觉走查清单(间距/对齐/层次/对比度/状态反馈)在亮色与暗色主题下逐条通过,通过率 100%。
- **SC-002**: 仅用键盘可完成核心流程全程,焦点可见且顺序合理,通过率 100%。
- **SC-003**: 在标准视口断点集合(sm 640 / md 768 / lg 1024 / xl 1280 / 2xl 1536)下无横向滚动条、无内容溢出,通过率 100%。
- **SC-004**: 在 500+ 书签数据集下,首屏 LCP < 1.5s、TTI < 2s(中端移动 + 3G 模拟)、INP < 200ms、CLS < 0.1 达标率 100%。
- **SC-005**: 暗色/亮色主题切换无闪烁(无 FOUC),主观即时一致。
- **SC-006**: 极端字段(超长标题/favicon 缺失/无效 URL)下布局不被破坏,通过率 100%。

## Assumptions

- "沿用当前设计"= 不改整体框架、不更换 UI 组件库、不更改数据存储方式;其余视觉/交互/适配/性能细节皆可优化。此为硬约束。
- 四维度优先级按描述顺序:视觉 P1、交互 P2、适配 P3、性能 P4,各自可独立交付与验收。
- 性能基线采用通用 Web 指标(LCP/INP/CLS 的通用阈值),具体阈值可在 `/speckit-clarify` 阶段收紧。
- "标准视口断点集合"暂取 360/480/768/1024/1440 px,具体断点可在 clarify 阶段调整。
- 无障碍对比度标准采用 WCAG AA(正常文本 4.5:1,大文本 3:1)。
- 大数据量性能验收数据集规模暂取 500+ 书签,具体规模可在 clarify 阶段调整。
- 具体优化项(改哪些间距、加哪些动效、补哪些断点、优化哪些渲染)不在本 spec 枚举,留给 `/speckit-clarify`。
